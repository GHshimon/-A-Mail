# Seed Brief — A-mail「信頼できる個人用AIメールアシスタント」

## 観測事実

### プロジェクトの現在地

- A-mailは、Gmail／iCloudを扱うmacOS向けの個人用メールクライアントとして設計されている。
- 技術構成はTauri v2、Rust、React、TypeScript、SQLite、macOS Keychain、Gemini API。
- メールの閲覧、作成、送信、下書き、検索、添付保存、AI補助までをMVP範囲としている。
- AI補助には、予測入力、関連メールの要点整理、返信ドラフト生成、新着メール分類がある。
- AI機能は既定で無効であり、利用者が有効化した場合だけメール情報を外部へ送信する設計になっている。
- 配布、App Store申請、OAuth、カレンダーや連絡先本体との連携は当面の対象外である。

### 現在確認されている困りごと

- `main@4587af5`の動作確認で、返信ドラフト生成後に、それまで表示されていた要点が壊れたJSONへ置き換わり、返信本文も宛名と挨拶だけで途切れる症状が報告されている。
- 登録資料では、次の組み合わせが原因として特定されている。
  - ドラフト本文の変化によって要点取得が再実行される。
  - 要点生成と返信生成が同じ512トークンの出力設定を共有している。
  - 思考トークンが出力枠を消費する。
  - JSONの解析失敗時に、途中で切れた生テキストを「経緯」として表示する。
- Claude側ブランチとmainでは、同じ`PRAGMA user_version`番号に異なるDB変更が割り当てられている。
- 監査時点の実DBはClaude系列の`user_version = 4`であり、main側の一部スキーマは適用されていない。
- 統合前のmainビルドを実DBへ接続すると、必要な移行が飛ばされたままバージョンだけ進む危険が報告されている。
- 文字化け対策、IMAP接続再利用、差分同期、本文先読み、添付保存、AI分類、参考ファイル機能など、統合時に保持すべき変更がClaude側に存在する。
- 作業リスト上では、AI出力切り詰め不具合と、Claude側の必須機能をmainへ統合する作業が未着手として残っている。

## 提案

### 企画の種

A-mailを、単に文章を生成するメールアプリではなく、**利用者が根拠と送信範囲を確認しながら、安全に返信判断を進められる個人用AIメールアシスタント**として仕上げる。

### 解決したい中心課題

メール処理では、過去の経緯、相手から求められていること、不足情報、次の行動を利用者自身が再構成する必要がある。AIはこの負担を減らせる一方、出力の切り詰めや解析失敗を正常な要点として表示すると、誤った理解や内容のない返信を生む。

そのため、生成速度や機能数より先に、次の状態を成立させる。

- 読み取れなかった内容を、読み取れた事実として表示しない。
- 受信メール上の依頼事項と、AIが指摘した不足情報を区別する。
- AIへ送る情報の範囲を利用者が確認できる。
- 生成後も、それまで確認した要点が意図せず失われない。
- DB移行やブランチ統合によって既存メールを損なわない。

### 最初に成立させる体験

1. 利用者が受信メールを開く。
2. A-mailが経緯、相手からの依頼、期限、未対応事項を整理する。
3. 解析に失敗した場合は、壊れた内容を表示せず取得失敗を明示する。
4. 利用者が要点を確認してから返信ドラフトを生成する。
5. ドラフト生成後も要点は維持され、本文編集による不要な再取得は発生しない。
6. 利用者が内容を編集・承認した後にだけ送信する。

### 最小の実施範囲

- 要点生成、返信生成、予測入力で生成設定を分離する。
- 構造化出力では思考を無効化し、必要な出力枠を確保する。
- 不正なJSONを要点へ変換するフォールバックを廃止する。
- 要点を取得できない状態をUIで明示する。
- 本文変更を要点再取得のトリガーから外す。
- 表示するモデル名を実際の設定値と一致させる。
- 架空メール、偽のAI応答、インメモリまたは一時DBで回帰試験を行う。
- 既存成果物は上書きせず、新しい実装・検証成果として段階的に追加する。

### 安全境界

- 実メールを自動送信しない。
- AI機能を自動で有効化しない。
- パスワードとAPIキーを画面、DB、ログへ露出させない。
- 統合方針が確定するまで、mainビルドを既存の実DBへ接続しない。
- OAuth、別AIプロバイダ、外部カレンダー、外部連絡先、アプリ配布は初期範囲に含めない。
- ブランチ統合では、文字化け対策、IMAP性能対策、データ品質修正、送信範囲表示を退行させない。

### 成功の判断基準

- 2,000文字以上の日本語メールでも要点が構造化データとして解釈できる。
- AI応答を故意に途中で切った場合、壊れたJSONを「経緯」として表示しない。
- 要点を取得できなかった場合、その状態が利用者に明示される。
- 返信ドラフト生成後や本文入力中に、要点取得が再実行されない。
- 返信本文が宛名と挨拶だけで終了しない。
- 表示中のモデル名と実際の設定値が一致する。
- Claude系列、main系列、新規、部分適用済みの各DBを、安全なテスト用DB上で統合できる。
- 移行を複数回実行しても、データ消失や重複変更が発生しない。

### 次の判断材料

1. **最優先課題**  
   AI切り詰め不具合の修正を、機能追加や全面統合より先に実施するか。

2. **DB移行方式**  
   `user_version`だけに依存せず、テーブルや列の存在を確認する名前付き・冪等な互換移行方式を採用するか。

3. **統合順序**  
   「不具合修正と偽データ試験」→「互換移行の試験」→「必須保持機能の段階統合」→「実機確認」の順で進めるか。

4. **関連メールの表示契約**  
   AIへ実際に送った範囲を示す専用要約型を維持するか、通常のメール一覧型へ統合するか。

5. **参考ファイル機能の入口**  
   明示的なファイル選択UIを、main側のプロジェクト登録・検索機構へ一本化するか。

6. **MVP後の優先順位**  
   通知、IMAP IDLE、スレッド表示、送信添付のうち、どれを次工程の対象とするか。
